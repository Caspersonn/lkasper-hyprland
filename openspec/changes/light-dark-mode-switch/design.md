## Context

The archived `wallpaper-driven-theming` change built a wallpaper-derived base16 pipeline: `regenerate-palettes.sh` commits one palette per wallpaper, `themes.nix` feeds the active one into `nix-colors` `colorScheme`, and AGS reads `themes/<slug>/colors.json` at runtime and recolours via GTK `@define-color`. It deliberately resolved light/dark as *"force dark"*.

Three things block a light/dark switch, all verified in the current tree:

1. `regenerate-palettes.sh` hardcodes `palette = "ansidark16"`, which always yields a near-black `base00`. Even `beach-light.json` is a dark palette (`base00 = 000C00`).
2. `envs.nix` sets `GTK_THEME = "Adwaita-dark"` and `ADW_DISABLE_PORTAL = "1"` in both `home.sessionVariables` and the Hyprland `env` block. `GTK_THEME` overrides gsettings for GTK3 *and* GTK4, per session.
3. Only AGS and Hyprland borders follow `theme-switch`. Everything else is baked at build time, and the four activation-written files (`hypr/theme.conf`, `btop/themes/lkh-runtime.theme`, `ghostty/themes/lkh-runtime`, `starship.toml`) are guarded by `if [ ! -f ]` — written once, never refreshed. `hypr/theme.conf` *is* sourced (last, from `_hyprland/configuration.nix` `extraConfig`), so it silently overrides `looknfeel.nix`'s border colours with whatever the first-ever activation wrote.

## Goals / Non-Goals

**Goals:**
- One keybind flips the whole desktop between light and dark with no rebuild.
- Light palettes are natively generated by wallust and keep ANSI slot semantics (red is red) so terminals stay trustworthy.
- Every themed app reads the active theme through one indirection, so adding a consumer is a template, not a code path.
- `current/` is a stable cross-repo contract the `nixvim` repo can consume without a flake dependency.

**Non-Goals:**
- Implementing the nixvim side (contract only).
- Light/dark icon theme variants.
- Cross-fade or animated mode transitions.
- Sourcing light siblings for the four wallpapers being removed.

## Decisions

### D1 — Wallpapers are pairs; mode swaps image and palette together
A wallpaper is a **pair** with a `light` and `dark` member, declared explicitly in `wallpapers/pairs.nix`. Theme state is `(pair, mode)` and resolves to exactly one image and one palette.

An explicit Nix registry beats a filename convention (`*-light`/`*-dark`) because it allows siblings with unrelated names and makes completeness checkable. `themes.nix` asserts that every image in `wallpapers/` belongs to exactly one pair, so an unpaired image fails evaluation instead of producing a ghost theme.

**Consequence:** one palette per *image*, not two per image — the member's role in the pair selects the generator flavour. **Alternatives:** two palettes per image with the wallpaper held constant (rejected by the user: mode should swap the image); convention-based pairing (rejected: not enforceable, no unrelated-name pairs).

### D2 — Light palettes: `lchansi` + `light16` does not work (measured)
Spiked against `beach-light.png`, counting ANSI slots more than 45° off their canonical hue:

| colour_space + palette | off-hue |
| --- | --- |
| `lchansi` + `ansidark16` on `beach-dark.png` (today's dark baseline) | 1/7 |
| `lchansi` + `ansidark16` on `beach-light.png` | **0/7** |
| `lchansi` + `light16` | 5/7 |
| `lchansi` + `softlight16` | 7/7 |
| `lch` + `light16` | 6/7 |

wallust has no `ansilight16`; `lchansi`'s ANSI preservation only holds with the `ansidark` family, exactly as its own docs hedge. The failure is a slot swap, not a tint: `base0B` ("green") came back `#0058BF` at hue 212° and `base0D` ("blue") came back `#3A9367` at hue 150°, which would render `git diff` additions in blue. Rejected.

Note also that `softlight16` is not light polarity at all (`base00 = #4E4C4B`), so `light16` is the only usable light palette.

### D3 — Light palettes: split the shell from the hues, then clamp down
Hue extraction was never the problem — palette *polarity* was. So the two concerns are generated separately from the same image and merged:

```
  light member image
      ├── lch     + light16     ──▶ base00–base07   the light shell (bg/fg/greys)
      └── lchansi + ansidark16  ──▶ base08–base0F   ANSI-faithful hues (0/7 off)
                                         │
                                   clamp to ≥ 4.5:1 on base00
```

The clamp lowers HSV value only, preserving hue and saturation. Measured on `beach-light.png`: maximum hue drift 0.3°, maximum Δvalue 0.21, and two slots needed no change at all. Every slot lands at WCAG AA against the light background.

This mirrors the generator's existing shape — it already runs wallust twice per image (base16 + accents) and merges the results — so this is a third run in an established pattern, not new machinery.

### D4 — The contrast clamp inverts with mode
Dark mode floors accent brightness (`v ≥ 0.55`) so accents read on a near-black bar. Light mode must do the opposite: darken until contrast against `base00` reaches 4.5:1. Getting this wrong is catastrophic rather than cosmetic — `beach-light`'s third accent `#C3FCDF` (pale mint) sits at **1.13:1** on the light background, i.e. invisible, and the clamp takes it to `#607B6D` at 4.54:1.

**Accepted trade-off:** a pale accent can only reach contrast by becoming muted (mint → sage). We clamp value only, because it is measured and preserves hue exactly. If the result reads as drab, the knob is to raise saturation as value drops; deferred until seen on a real screen.

### D5 — `light16` collapses the shell ramp; derive the surfaces
`light16` through the existing `base16-template.json` produces byte-identical slots:

```
base00 #F7FFFC ┐ identical   (base00={{background}}, base01={{color0}},
base01 #F7FFFC ┘              and light16 sets color0 ≈ background)
base02 #89B09C ┐ identical
base03 #89B09C ┘
base04 #120D05 ┐
base05 #120D05 ├ identical   (base04={{color7}}, base06={{color7}})
base06 #120D05 ┘
```

This is structural — a property of the template mapping, not of the image. `base04≈05≈06` is the collapse bean `9ura` already documented for dark mode, and its fix carries over untouched: AGS ramps dim/faint off `alpha(@base05, …)`, which is polarity-agnostic. But `base00 == base01` is new and worse, because AGS uses `base01` as `$surface0` — a light bar would have zero surface separation. The generator therefore **derives** `base01`/`base02` for light palettes by stepping `base00` toward `base05` instead of taking `color0`/`color8`.

### D6 — Propagation: Nix renders every combination, switching is one relink
Nix generates a complete config bundle for each `(pair, mode)` into the store. `~/.config/lkasper-hyprland/current` is a runtime-owned symlink at the active bundle, and every consumer reads through it.

```
  themes/<pair>/<mode>/{colors.json,colors-ansi.json,foot.ini,btop.theme,
                        ghostty,starship.toml,hypr.conf,hyprlock.conf,
                        gtk.css,opencode.json,nvim.lua,wallpaper.path}

  ~/.config/lkasper-hyprland/current ──▶ themes/beach/dark
  ~/.config/lkasper-hyprland/state   ──▶ "beach dark"
```

Considered and rejected: **(A) runtime templating** — `theme-apply` renders each app's config from JSON with jq, which duplicates every template in shell and re-introduces build/runtime skew; **(B) rebuild to switch** — fully declarative but ~30s per toggle, unusable on a keybind. C keeps all rendering in Nix, makes switching atomic, and costs a few kilobytes of text per combination.

C also settles the open question the archived design left dangling — *"does a rebuild stomp a runtime selection?"* Because `current` is created by the activation script only when absent and is never a `home.file`, a rebuild leaves a runtime selection alone.

### D7 — Consumers reach the bundle through stable symlinks, not through Nix
Apps whose config path cannot itself vary are wired once, in activation, with a symlink into `current/`:

| App | Wiring | Reload on switch |
| --- | --- | --- |
| AGS | reads `current/colors.json` | live (`App.apply_css`) |
| Hyprland | `extraConfig` sources `current/hypr.conf` last | `hyprctl reload` |
| foot | top-level `include=` in a hand-written `foot.ini` | `SIGUSR1` |
| GTK / libadwaita | `gsettings color-scheme` + `gtk.css` symlink | live |
| hyprlock | `settings.source` + `sourceFirst`, `$lkh_*` vars | next launch (always fresh) |
| ghostty | `themes/lkh-runtime` → `current/ghostty` | live via the `reload-config` D-Bus action |
| btop | `themes/lkh-runtime.theme` → `current/btop.theme` | next launch |
| starship / opencode | config path → `current/…` | next shell / restart |
| neovim | reads `current/nvim.lua` | out of scope (contract only) |

foot needs a hand-written `foot.ini` because its `include=` is a default-section directive and `pkgs.formats.ini` (which home-manager's `programs.foot.settings` uses) cannot emit a top-level scalar key. Setting `settings = { }` disables home-manager's file so ours takes over.

### D8 — AGS light mode is a token flip plus a delta sheet, not a second stylesheet
An audit of all 1713 lines of `style.scss` found exactly eight dark-surface assumptions — white hairlines and black shadows at lines 52, 1291, 1294, 1380, 1381, 1464, 1546, 1590. Everything else already survives inversion, because the hierarchy is built from `alpha(@base05, …)` ramps off the *foreground* token.

So those eight become two new named colours, `hairline` and `shade`, injected per mode by `theme.ts`, plus `light.scss` carrying the genuine light-mode differences (shadow weight, translucency). The shared helpers and colour tokens move to `_tokens.scss` so both sheets can `@import` them.

**Alternative rejected:** two full 1713-line stylesheets. The audit says there is nothing structural to diverge about, and a fork would drift on every future widget edit.

### D9 — GTK follows the Settings portal, not an env var
`GTK_THEME` and `ADW_DISABLE_PORTAL` are removed from both `home.sessionVariables` and the Hyprland `env` block, and `programs.dconf.enable` is set in `modules/nixos/hyprland.nix`. `theme-apply` then sets `color-scheme` and `gtk-theme` via `gsettings`, which the already-correctly-configured `xdg-desktop-portal-gtk` Settings portal (`modules/nixos/hyprland.nix:24`) carries to libadwaita apps live.

The `ADW_DISABLE_PORTAL` comment claiming the portal is broken turned out to be **accurate**, and my first explanation for it was wrong. dconf works fine — measured on the live machine, `gsettings get org.gnome.desktop.interface color-scheme` returned `prefer-light` and persisted. The real cause is D11.

Ordering therefore matters: removing `ADW_DISABLE_PORTAL` is only correct *together with* the D11 fix. Remove it while the Settings portal is still absent and libadwaita has nothing to read at all.

### D11 — home-manager's `xdg.portal` shadows the system portal directory
The XDG portal exposed no `Settings` interface — nor `FileChooser`, `Print` or `Account`. The NixOS-level `xdg.portal.extraPortals = [ xdg-desktop-portal-gtk ]` in `modules/nixos/hyprland.nix` was correct and entirely ineffective, because home-manager's `xdg.portal` module (enabled transitively by the HM hyprland module) sets

```
NIX_XDG_DESKTOP_PORTAL_DIR = ~/.nix-profile/share/xdg-desktop-portal/portals   # only hyprland.portal
```

overriding the system value

```
NIX_XDG_DESKTOP_PORTAL_DIR = /run/current-system/sw/share/…/portals            # gtk.portal + hyprland.portal
```

The frontend log names it exactly: `Requested gtk.portal is unrecognized`, then `Requested backend hyprland.portal does not support org.freedesktop.impl.portal.Settings. Skipping...`. The portal *config* was fine all along (`default=hyprland;gtk`); the definition file was simply not on the search path. Starting `xdg-desktop-portal-gtk.service` by hand does not help — the missing piece is the `.portal` file, not the backend process.

Fix: add `xdg-desktop-portal-gtk` to the **home-manager** `xdg.portal.extraPortals`, so the user-profile directory carries `gtk.portal`. Verified by pointing the variable at the system directory and restarting the frontend: `Settings.ReadOne(org.freedesktop.appearance, color-scheme)` returned `uint32 2` and the gtk-backed interfaces appeared.

This is wider than theming — it also restores the GTK file chooser and print portals for Firefox and Electron apps.

### D10 — Neovim gets a contract in this change, an implementation in another
The bundle emits `nvim.lua` (a table of the ANSI-faithful palette plus `mode`) and `colors-ansi.json`. The `nixvim` repo reads the well-known path and falls back to melange when it is absent, so nixvim stays usable standalone and neither repo gains a flake input on the other.

Neovim must read the **ANSI-faithful** palette, not `colors.json`: `themes.nix` deliberately remaps `base0A`–`base0F` onto the three-colour accent triple for AGS, which collapses several slots onto the same hue. Feeding that to a syntax highlighter would make strings, types and keywords look alike.

## Risks / Trade-offs

- **A pale accent goes muted in light mode** (D4, accepted) → clamp value only for now; saturation compensation is the knob if it reads drab.
- **Removing `GTK_THEME` may leave GTK3 apps mid-toned** if the portal path is still broken → mitigation in D9; verifiable in one command (`gsettings get org.gnome.desktop.interface color-scheme`).
- **Light-mode legibility on a wallpaper-derived palette is unproven on a real screen** → `check_contrast` plus the D4 clamp plus the D5 derived surfaces are all guardrails, but the first real verdict is visual.
- **`ansidark16` hues on a light background are AA, not AAA** → 4.5:1 is the target; small text on an accent-coloured fill may still feel thin.
- **Store size grows with pairs × modes** → text only, kilobytes; not a real cost even at a dozen pairs.

## Migration Plan

1. Delete the four unpaired wallpapers' palettes and the dead `modules/_themes.nix`; add `wallpaper.ignored/` to `.gitignore`.
2. Add `wallpapers/pairs.nix` and the eval-time pairing assertion.
3. Rewrite the generator pair-aware with the light pipeline (D3/D4/D5); regenerate and commit both `beach` palettes.
4. Rewrite `themes.nix` to emit the per-`(pair, mode)` bundle, the `current` symlink, and `theme-apply` / `theme-toggle` / `theme-switch`; drop the `if [ ! -f ]` guards.
5. Repoint each consumer at `current/` (D7); remove the static border colours from `looknfeel.nix` and repoint `configuration.nix`'s `extraConfig` source from `hypr/theme.conf` at the bundle.
6. Remove `GTK_THEME` / `ADW_DISABLE_PORTAL`; enable `dconf` (D9).
7. AGS: `_tokens.scss` + `light.scss` + tokenise the eight sites; make `theme.ts` mode-aware (D8).
8. Update the picker to list pairs; add the toggle keybind.

**Rollback:** revert the change commit. The `current` symlink and `state` file are runtime-only and harmless if left behind.

## Open Questions

- **Icon theme** — `Gruvbox-Plus-Dark` has no light sibling, so icons stay dark-tuned in light mode. Deferred to a follow-up bean; needs a light-capable icon set (e.g. Papirus) to be worth doing.
- **Qt apps** — `QT_STYLE_OVERRIDE` is `adwaita` in `home.sessionVariables` but `kvantum` in the Hyprland `env` block, which is already inconsistent. Whether Qt follows `color-scheme` live is untested and out of scope.
- **ghostty live reload** — RESOLVED: ghostty 1.3 exports a `reload-config` action on `org.gtk.Actions` at `com.mitchellh.ghostty`, so `theme-apply` triggers it over D-Bus (guarded by a `ListNames` check so it never D-Bus-activates a ghostty that is not running). `gtk-single-instance = true` made this necessary rather than optional: new windows come from the existing process, which had already loaded the old theme, so without the reload ghostty would only re-theme on a full restart.
